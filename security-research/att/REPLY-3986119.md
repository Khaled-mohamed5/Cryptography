Hi @h1_analyst_decimo, thanks for picking this up.

Those four data points — source IP, hostname, username, and working directory — come from a
callback fired by a package published under the scope. As stated in the report, **I have not
registered `@att-bit` and have not published any package**, so I have no callback data to
share.

That was a deliberate choice, for three reasons:

1. **Publishing would execute my code on AT&T build infrastructure.** The program excludes
   "Attacks against AT&T infrastructure" and states "You may only exploit, investigate, or
   target vulnerabilities against your own accounts." A `postinstall` script running on an
   AT&T CI runner is squarely within that exclusion.

2. **The scope lives on npmjs.com, not on an AT&T asset.** Registering `@att-bit` is an action
   against the public npm registry, whose terms prohibit claiming namespaces that impersonate
   another organisation. Neither AT&T nor HackerOne is in a position to authorise that on
   npm's behalf.

3. **I could not control who received the package.** Anything published to that scope would be
   installed by whatever build resolved it first — potentially a contractor's workstation or a
   partner's pipeline, belonging to people who have not consented to testing.

**What the report does establish**, both halves verifiable by you in under a minute without
touching any AT&T system:

- AT&T production JavaScript at `accsupport.att.com` imports from the `@att-bit` scope
  (evidence: the source map, publicly served)
- That scope returns `404` across the public npm registry, so it is unregistered and available
  to any third party (evidence: the registry API responses)

**Determining whether an AT&T build actually falls back to the public registry is something
AT&T can answer internally and I cannot** — it requires either registry-side telemetry or
inspecting `.npmrc` distribution across CI images and developer environments. I would suggest
checking whether any build image, container definition, or CI runner omits a
`@att-bit:registry=` entry.

Regardless of that answer, the remediation is the same and costs nothing: register the
`@att-bit` scope under an AT&T-controlled npm account and publish placeholder packages for the
names in use. That permanently removes the possibility of a third party claiming it.

If AT&T's security team would like a controlled demonstration notwithstanding the above, please
have them confirm in writing on this report what they are authorising and how they would like
it coordinated with npm. I am happy to assist within whatever scope they define, but I am not
going to publish to that namespace on my own initiative.

Happy to answer anything else.
